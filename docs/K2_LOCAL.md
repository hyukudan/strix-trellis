# K2/R1: LDS split reduction and early loads

> **Type:** design note — engineering record; may describe plans, candidates or experiments that are not part of the supported API.

## Status and purpose

This candidate is experimental and disabled by default. It builds only with
`STRIX_TRELLIS_BUILD_EXPERIMENTAL_K2_LOCAL=ON`. Qualified V16 selection remains
unchanged: `backend.hip`, `gemv_lds.hip` and `gemv_k2.hip` have not been changed
to select this path. It requires `gfx1151`, wave32 and integer-bit K2/mul1 weights.

The qualified path already grouped four K16 reads before consuming them.
The change here places the four K splits for one N16 output in the four waves
of a 128-thread block. Each wave keeps its K interval, product order and
four-lane reduction. It writes its 16 results to LDS. After a convergent barrier,
the first wave sums the splits in order 0, 1, 2, 3, starting from +0, and writes
a single global plane.

The reduction uses 256 bytes of LDS. Global partials shrink from four F32 planes
`[4,N]` to one plane `[N]`. The output transform keeps H128, `svh`, bias and
alpha/beta, and receives `splits=1` because the sum has already been computed.
The complete operator still uses three launches. Weights are not materialized
in FP16. This traffic reduction is not a DRAM measurement.

| Geometry | V16 workspace, bytes | Candidate workspace, bytes | Workspace reduction |
|---|---:|---:|---:|
| I=8192, N=5120 | 98304 | 36864 | 62.5% |
| I=1280, N=32768 | 526848 | 133632 | 74.6% |

These sizes are derived from code, not speed measurements. Both matrices retain
10,485,760 bytes of compressed weights. Reducing partials does not imply a
fourfold operator speedup. Distributing reads across waves may change cache
behavior.

Five variants are available: U1, U2, U4, Pipeline2 and Pipeline4. The last two
expose loads for the next batch before consuming the current batch. These are
ordinary C++ loads visible to LLVM. They contain no hidden asynchronous memory
instructions and do not manually force `waitcnt`. The ISA must show whether the
compiler overlaps loads with useful work. More live registers may make a
variant with more lookahead slower.

## Reproducible build

Run from a dedicated checkout under `<scratch dir>`.
These commands compile; they do not execute GPU work:

```sh
nice -n 10 cmake -S . -B build-k2-local \
  -DSTRIX_TRELLIS_ENABLE_HIP=ON \
  -DSTRIX_TRELLIS_BUILD_EXPERIMENTAL_K2_LOCAL=ON \
  -DCMAKE_HIP_COMPILER=/opt/rocm/core-10.1/lib/llvm/bin/clang++ \
  -DCMAKE_HIP_COMPILER_ROCM_ROOT=/opt/rocm/core-10.1 \
  -DCMAKE_PREFIX_PATH=/opt/rocm/core-10.1 \
  -DCMAKE_HIP_ARCHITECTURES=gfx1151
nice -n 10 cmake --build build-k2-local --parallel 1 \
  --target strix_trellis_k2_local_probe
```

The memory-policy and size test also runs in CPU CI as `k2_local_policy`.
It does not establish numerical correctness or GPU performance.

K2 fixtures are synthetic, reproducible and bounded. They do not download models:

```sh
nice -n 10 python3 tools/make_k2_fixtures.py --out "$PWD/k2-local-fixtures"
```

The `wo_b.stgpu` and `q_b.stgpu` files generated by the same tool may also be
reused after verifying their manifest and hashes. Their K2 content is synthetic
even when dimensions correspond to real projections.

## Execution through the allocated GPU slot

The checkout, executable and fixtures must be available on the test machines
with identical paths and hashes. `tools/run_gpu_turn.sh` wraps a site-specific
GPU queue script (not part of this repository). The runner checks maintenance,
site-specific quiet hours and maximum duration. Never invoke `--inside` directly.
The full test uses the same mechanism as the rest of the project:

```sh
bash tools/run_gpu_turn.sh --seconds 600 \
  --maintenance-check "$PWD/tools/check_maintenance.sh" \
  --queue-arg strix-trellis-k2-local -- \
  "$PWD/build-k2-local/strix_trellis_k2_local_probe" \
  "$PWD/k2-local-fixtures/wo_b.stgpu" \
  "$PWD/k2-local-fixtures/q_b.stgpu"
```

Without fixture arguments, the executable runs only the exhaustive decoder check
and small geometries. It writes `LOCAL_LARGE NOT_RUN`. That result does not
qualify the complete operator, graphs or performance.

## What the probe checks

- All hash states and FP16 pairs, including high-bit contamination, and reader
  states with basis vectors and random data.
- Empty splits, K bounds that are not multiples of U2/U4, N16/N48 outputs,
  comparison of every output against CPU FP64 and the control's ordered sum.
- Rejection of invalid alignments, aliases and variants before launching work.
- In both large geometries, all complete-operator columns, bias present/absent,
  alpha/beta and output previously poisoned with NaN when beta is zero. Results
  must match V16 byte for byte and pass the declared CPU oracle.
- Three-kernel capture/replay, no nodes for invalid arguments, canaries and
  comparison of each weight copy's outputs before and after timing.
- Eleven sweeps alternating the order of the six paths over independent weight
  addresses, with at least 256 MiB resident. Check the final timed output and
  traverse every address again.

`LOCAL_RESULT protocol=operator` is the relevant complete comparison.
`schedule=v16` lines use the V16 backend and kernels rebuilt into the same
binary. They do not link the archived qualified library or include C API
validation. `protocol=core` lines explicitly report four planes for V16 and one
for the candidate: the final buffers of these two measurements have different
semantics. `compressed_GBs` uses weight bytes divided by operator time;
`useful_TOPS` uses `2*I*N/time` (operator time). Neither is a physical DRAM counter or full-model
throughput. Host time includes queue completion and is reported separately from
event time.

Before promoting a variant, archive the commit, commands, compiler, flags,
source/binary/fixture hashes, test-machine hardware, clocks/power/temperature and
complete logs. Extract ISA and ELF notes to verify wave32, registers, LDS,
private memory/spills and actual load/wait placement. The gain must repeat
against V16 in the same GPU slot and in an independent confirmation, without
numerical regression. This work includes no new GPU measurements.

## Region-loading and prepared-plan QA

`strix_trellis_prepared_api_probe` validates the new APIs with qualified kernels.
It does not use the K2 candidate to demonstrate loading or host improvements.
Build it with HIP and execute it through the same runner:

```sh
nice -n 10 cmake --build build-k2-local --parallel 1 \
  --target strix_trellis_prepared_api_probe
nice -n 10 python3 tools/make_gpu_fixtures.py \
  --skip-real --out "$PWD/prepared-api-fixtures"
bash tools/run_gpu_turn.sh --seconds 600 \
  --maintenance-check "$PWD/tools/check_maintenance.sh" \
  --queue-arg strix-trellis-prepared-api -- \
  "$PWD/build-k2-local/strix_trellis_prepared_api_probe" \
  "$PWD/prepared-api-fixtures/synthetic-mul1-k2-i128-n256.stgpu" \
  "$PWD/prepared-api-fixtures/synthetic-mul1-k5-i256-n128.stgpu"
```

These fixtures include R1, R8 and prefill R32, with and without bias. The probe
checks weights loaded from unaligned host regions freed after preparation,
equivalence with blob transport, the CPU reference, alpha/beta, frozen
descriptors, weight retention, capture/replay and canaries. With fixtures
containing more rows, it adds R128/R256. The host comparison reports submit
time, event time and completion time using the same weights and hot addresses.
Submit may include runtime backpressure, and events may include gaps between
submissions. Do not interpret these as memory bandwidth or the pure cost of
validation. Preparation and consumption are tested on the same stream; this
probe does not establish cross-stream coverage.
